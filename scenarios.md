9# Сценарии вариантов использования

## ВИ-06. Триггер прогона из CI

**Актёры:** CI-сервер (первичный, внешняя система), TestAPI, TestRunner, ReportService

**Цель:** по событию в репозитории (коммит, расписание) CI-сервер получает статус
прогона и отчёт, чтобы принять решение о gate сборки

**Предусловия:** интеграция с CI настроена (ВИ-05); CI-сервер аутентифицирован токеном;
набор тестов, привязанный к ветке, существует и активен

**Постусловия (успех):** создан Run (commitSha, triggerSource, статус PASSED/FAILED);
сохранены TestResult по каждому тесту; отчёт доступен по summaryUrl; CI-сервер получил
ответ со статусом и summaryUrl

**Постусловия (неуспех):** Run зафиксирован со статусом ERROR/CANCELLED и остаётся
в истории; CI-сервер получил отказной статус

**Тип:** базовый

**Связи:** include ВИ-01 «Запустить набор тестов»; результат потребляется шагом gate
сборки CI

### Основной сценарий

|#|Действие актёра|Отклик системы|
|-|-|-|
|1|CI-сервер по событию в репозитории отправляет POST /runs (suiteId, commit, ветка)|2. CI-адаптер TestAPI проверяет токен и нормализует параметры (commitSha, triggerSource)|
|||3. Система создаёт Run со статусом PENDING и фиксирует commitSha|
|||4. Система передаёт набор тестов TestRunner; Runner исполняет тесты во внешней среде|
|||5. Runner сохраняет TestResult по каждому тесту в RunHistory|
|||6. Система вычисляет итоговый статус прогона (PASSED/FAILED)|
|||7. ReportService строит отчёт; TestAPI возвращает CI-серверу summaryUrl и статус|

### Исключения

**И-1. Токен CI-сервера недействителен** (шаг 2)

CI-адаптер отклоняет запрос без создания Run (401). CI-сервер логирует отказ и завершает
сценарий; повтор возможен после обновления токена через ВИ-05.

**И-2. Набор тестов не найден или не привязан к ветке** (шаг 3)

Система отвечает ошибкой конфигурации, Run не создаётся. Требуется действие
разработчика: привязать набор к ветке или настроить интеграцию (ВИ-05). Прогон не
считается упавшим — он не состоялся.

**И-3. Внешняя среда исполнения недоступна или упала во время прогона** (шаг 4)

Runner фиксирует TestResult со статусом ERROR, Run переводится в ERROR. Отчёт
формируется с причиной сбоя окружения; CI получает статус ERROR — gate не пропускает
сборку, но тесты не считаются «красными»: падение инфраструктурное, а не продуктовое.

**И-4. Превышено время ожидания ответа** (шаг 7)

CI-сервер разрывает соединение по таймауту, но Run продолжает выполняться (асинхронность).
CI опрашивает статус по идентификатору Run; при повторе запроса система использует
идемпотентный ключ и не создаёт дубликат прогона.

### Примечания

Прогон асинхронный: gate-статус CI получает либо ответом, либо опросом — оба пути
возвращают один и тот же Run. Инфраструктурные падения (ERROR) принципиально отличаются
от продуктовых (FAILED): смешение этих статусов портит статистику стабильности.

## ВИ-04. Выявить и маркировать флаки-тесты

**Актёры:** Тестировщик (первичный — потребитель результата маркировки),
Система автоматического тестирования (RunHistory), CI-сервер (источник прогонов)

**Цель:** по итогам каждого прогона автоматически отличить нестабильный тест
от настоящего дефекта, чтобы флаки не блокировали релизный процесс

**Предусловия:** прогон завершён (Run в статусе PASSED/FAILED); у тестов накоплена
история результатов

**Постусловия (успех):** у выявленных флаки-тестов isFlaky=true и обновлён retryCount;
маркировка отражена в отчёте и истории прогонов

**Постусловия (неуспех):** маркировка не изменилась; в лог прогона записана причина
(недостаточно данных, инфраструктурный прогон)

**Тип:** автоматический, включается в каждый прогон

**Связи:** include из ВИ-01 «Запустить набор тестов»; результат просматривается в ВИ-03
«Просмотреть историю прогонов» и используется ВИ-07 «Перезапустить упавшие тесты»

### Основной сценарий

|#|Действие актёра|Отклик системы|
|-|-|-|
|1|Система завершила прогон (Run со статусом PASSED/FAILED)|2. Система выбирает историю результатов каждого теста за окно последних N прогонов|
|||3. Система проверяет: у теста есть и PASSED, и FAILED на одинаковом коммите и окружении|
|||4. Система помечает тест isFlaky=true, обновляет retryCount|
|5|Тестировщик открывает отчёт/историю|6. Система показывает флаки-тесты отдельным списком с динамикой падений; в итоговом статусе прогона флаки не блокируют gate|

### Исключения

**И-1. Недостаточно истории для решения** (шаг 3)

У теста меньше N результатов в окне (например, новый тест). Система не маркирует его
и помечает «недостаточно данных»; после накопления истории решение пересчитывается
автоматически.

**И-2. Тест стабильно красный** (шаг 3)

Тест падает на всех прогонах окна — это не флаки, а вероятный дефект. Система не ставит
isFlaky (ложная маркировка скрыла бы баг): тест остаётся в списке упавших и блокирует
gate как обычно.

**И-3. Прогон инфраструктурный (Run в ERROR)** (шаг 2)

Результаты прогона со статусом ERROR не учитываются в окне истории: падение окружения
не является сигналом о флаки-природе теста. Система пропускает такой прогон при расчёте.

**И-4. Тест изменился между прогонами окна** (шаг 3)

Если версия теста сменилась (правка его кода), система сбрасывает окно: старые
результаты не характеризуют новый тест и дают ложную маркировку. Расчёт ведётся только
по результатам текущей версии теста.

### Примечания

Главный риск реализации — цена ошибки маркировки: ложный флаки прячет реальный дефект,
пропущенный флаки ломает gate случайными падениями. Поэтому эвристика консервативна
(нужно и PASSED, и FAILED на одинаковом коммите), а сомнительные случаи (И-1, И-3, И-4)
разрешаются в пользу «не маркировать». Размер окна N и пороги — конфигурация,
не зашитая константа.
