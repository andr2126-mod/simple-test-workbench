# Сценарии вариантов использования

## ВИ-06. Запустить прогон по событию CI

**Актёры:** CI-сервер (первичный, внешняя система), Система автоматического тестирования

**Цель:** по событию в репозитории (коммит, расписание) инициировать прогон набора тестов и получить его итоговый статус и отчёт, чтобы принять решение о gate сборки

**Предусловия:** интеграция с CI настроена (ВИ-05); CI-сервер аутентифицируется токеном; набор тестов, привязанный к ветке, существует и активен

**Постусловия (успех):** создан Run (commitSha, triggerSource, итоговый статус PASSED/FAILED); сохранены TestResult по каждому тесту; построен отчёт, доступный по summaryUrl; CI-сервер получил идентификатор Run при приёме запроса, а итоговый статус и summaryUrl - при опросе

**Постусловия (неуспех):** Run не создан (И-1, И-2) либо зафиксирован со статусом ERROR и остаётся в истории (И-3); CI-сервер получил отказной статус

**Тип:** базовый

**Связи:** include ВИ-01 «Запустить набор тестов»; результат потребляется шагом gate сборки CI

### Основной сценарий

| # | Действие актёра | Отклик системы |
| --- | --- | --- |
| 1 | CI-сервер по событию в репозитории запрашивает прогон набора тестов, передавая набор, коммит и ветку | 2. Система проверяет токен CI-сервера и приводит параметры запроса к единому виду (commitSha, triggerSource) |
| | | 3. Система создаёт Run со статусом PENDING, фиксирует commitSha и идемпотентный ключ |
| | | 4. Система подтверждает приём запроса и возвращает CI-серверу идентификатор Run |
| | | 5. Система запускает тесты набора во внешней среде исполнения (ВИ-01) |
| | | 6. Система сохраняет TestResult по каждому тесту в истории прогонов |
| | | 7. Система вычисляет итоговый статус прогона (PASSED/FAILED) и строит отчёт |
| 8 | CI-сервер опрашивает статус прогона по идентификатору Run | 9. Пока прогон не завершён, система отвечает PENDING; по завершении - итоговый статус и summaryUrl |

### Исключения

**И-1. Токен CI-сервера недействителен** (шаг 2)

Система отклоняет запрос без создания Run. CI-сервер логирует отказ и завершает сценарий; повтор возможен после обновления токена через ВИ-05.

**И-2. Набор тестов не найден или не привязан к ветке** (шаг 3)

Система отвечает ошибкой конфигурации, Run не создаётся. Требуется действие разработчика: привязать набор к ветке или настроить интеграцию (ВИ-05). Прогон не считается упавшим - он не состоялся.

**И-3. Внешняя среда исполнения недоступна или упала во время прогона** (шаг 5)

Система фиксирует TestResult со статусом ERROR, Run переводится в ERROR. Отчёт формируется с причиной сбоя окружения; при опросе (шаг 9) CI получает статус ERROR - gate не пропускает сборку, но тесты не считаются «красными»: падение инфраструктурное, а не продуктовое.

**И-4. CI-сервер не получил подтверждение приёма (таймаут)** (шаг 4)

Run уже создан и продолжает выполняться. CI-сервер повторяет запрос с тем же идемпотентным ключом; система возвращает идентификатор уже созданного Run и не создаёт дубликат. Дальше сценарий продолжается с шага 8.

### Примечания

Прогон асинхронный: ответ на запрос подтверждает только приём (Run в статусе PENDING), а итоговый статус CI получает опросом по идентификатору Run. Такая модель необходима, потому что прогон набора может идти минуты (см. нефункциональное требование к ВИ-01 в traceability.md) и не помещается в один запрос. Инфраструктурные падения (ERROR) принципиально отличаются от продуктовых (FAILED): смешение этих статусов портит статистику стабильности.

## ВИ-04. Выявить и маркировать флаки-тесты

**Актёры:** Тестировщик (первичный - потребитель результата маркировки), Система автоматического тестирования, CI-сервер (источник прогонов)

**Цель:** по итогам каждого прогона автоматически отличить нестабильный тест от настоящего дефекта, чтобы флаки не блокировали релизный процесс

**Триггер:** завершение прогона; ВИ запускает сама система как часть ВИ-01 (include), без действий актёра

**Предусловия:** прогон завершён (Run в статусе PASSED/FAILED); у тестов накоплена история результатов

**Постусловия (успех):** у выявленных флаки-тестов isFlaky=true и обновлён retryCount; маркировка отражена в отчёте и истории прогонов

**Постусловия (неуспех):** маркировка не изменилась; в лог прогона записана причина (недостаточно данных, инфраструктурный прогон)

**Тип:** автоматический, включается в каждый прогон

**Связи:** include из ВИ-01 «Запустить набор тестов»; результат просматривается в ВИ-03 «Просмотреть историю прогонов» и используется ВИ-07 «Перезапустить упавшие тесты»

### Основной сценарий

| # | Действие актёра | Отклик системы |
| --- | --- | --- |
| | | 1. По завершении прогона система выбирает историю результатов каждого теста за окно последних N прогонов |
| | | 2. Система проверяет: у теста есть и PASSED, и FAILED на одинаковом коммите и окружении |
| | | 3. Система помечает тест isFlaky=true, обновляет retryCount |
| 4 | Тестировщик открывает отчёт или историю прогонов | 5. Система показывает флаки-тесты отдельным списком с динамикой падений; в итоговом статусе прогона флаки не блокируют gate |

### Исключения

**И-1. Недостаточно истории для решения** (шаг 2)

У теста меньше N результатов в окне (например, новый тест). Система не маркирует его и помечает «недостаточно данных»; после накопления истории решение пересчитывается автоматически.

**И-2. Тест стабильно красный** (шаг 2)

Тест падает на всех прогонах окна - это не флаки, а вероятный дефект. Система не ставит isFlaky (ложная маркировка скрыла бы баг): тест остаётся в списке упавших и блокирует gate как обычно.

**И-3. Прогон инфраструктурный (Run в ERROR)** (шаг 1)

Результаты прогона со статусом ERROR не учитываются в окне истории: падение окружения не является сигналом о флаки-природе теста. Система пропускает такой прогон при формировании окна.

**И-4. Тест изменился между прогонами окна** (шаг 1)

Если версия теста сменилась (правка его кода), система сбрасывает окно: старые результаты не характеризуют новый тест и дают ложную маркировку. Расчёт ведётся только по результатам текущей версии теста.

### Примечания

Главный риск реализации - цена ошибки маркировки: ложный флаки прячет реальный дефект, пропущенный флаки ломает gate случайными падениями. Поэтому эвристика консервативна (нужно и PASSED, и FAILED на одинаковом коммите), а сомнительные случаи (И-1, И-3, И-4) разрешаются в пользу «не маркировать». Размер окна N и пороги - конфигурация, не зашитая константа.
