    

# Спорные решения доменной модели

### Р-1. TestResult — композиция в Run, а не агрегация

**Альтернатива:** агрегация — результат мог бы существовать сам по себе.
**Решение:** композиция Run "1" *-- "1..*" TestResult.
**Почему:** результат теста вне прогона бессмыслен: непонятно, когда и в каком окружении
он получен и на какой коммит ссылается. Удаление прогона удаляет его результаты — иначе
статистика считает фантомы. Кратность со стороны Run ровно 1: результат не может
принадлежать двум прогонам (повтор создаёт свои результаты, а не переиспользует чужие).
**Что будет, если ошиблись:** «осиротевшие» результаты ломают расчёт флаки (И-3
сценария ВИ-04) и падают при построении отчёта.

### Р-2. Кратность повтора — 0..1, а не 1

**Альтернатива:** Run --> "1" Run — каждый прогон обязан быть чьим-то повтором.
**Решение:** Run "0..*" --> "0..1" Run.
**Почему:** повтор — опциональное поведение (extend ВИ-07, условие «есть упавшие»).
У исходного прогона повтора может не быть никогда, поэтому 0..1; повторов может быть
сколько угодно, и все ссылаются на один исходный прогон.
**Что будет, если ошиблись:** объектная диаграмма не соберётся для первого же прогона
без повтора — модель потребует несуществующий объект.

### Р-3. Привязка «набор ↔ ветка» — обошлись без класса-ассоциации

**Альтернатива:** класс-ассоциация Привязка(CIIntegration, TestSuite) с атрибутом ветка.
**Решение:** ассоциация CIIntegration "0..*" -- "0..*" TestSuite с атрибутом «ветка».
**Почему:** у связи одна роль — имя ветки; класс ради одного строкового атрибута
усложняет модель без выгоды. Критерий пересмотра: появятся per-pair настройки
(retry-политика ветки, расписание) — станет классом-ассоциацией Привязка.
**Что будет, если ошиблись:** миграция данных при появлении per-pair настроек —
дешевле, чем держать пустой класс «на всякий случай».

### Р-4. Пакеты — по направлению изменчивости и зависимостей

**Принцип:** management — стабильное ядро (что хранится), execution — изменчивая часть
(что происходит), integration — внешний интерфейс (как мир попадает в систему).
Зависимости строго ацикличные: integration → execution → management. Ядро не знает ни
о прогонах, ни об интеграции: смена CI-провайдера не трогает TestSuite/TestCase.
**Почему не по техническим слоям:** разбиение «репозитории/сервисы/контроллеры»
отражает реализацию, а не предметную область.

### Р-5. «Флаки-тест» — атрибут, а не класс

**Альтернатива:** класс FlakyTest, отдельный от TestCase.
**Решение:** TestCase.isFlaky: Boolean (+ retryCount).
**Почему:** флаки — состояние теста, меняющееся по мере накопления истории, а не
сущность. Отдельный класс породил бы дубль идентичности: тот же тест существовал бы
дважды, и историю результатов пришлось бы разрывать между ними.
**Что будет, если ошиблись:** тест, ставший флаки, пришлось бы «переносить» между
классами, теряя историю — именно её эвристика и анализирует (ВИ-04).

### Р-6. TestSuite — агрегация прогонов, а не композиция

**Альтернатива:** композиция — удаление набора удаляет его прогоны.
**Решение:** агрегация TestSuite "1" o-- "0..*" Run.
**Почему:** история прогонов переживает сам набор: набор можно расформировать, но
статистика стабильности обязана остаться (README: история помогает отслеживать
динамику). Композиция, в отличие от Р-1, разрушила бы главную ценность системы.
**Что будет, если ошиблись:** удаление устаревшего набора стёрло бы историю команды
и обнулило окно N для расчёта флаки.
