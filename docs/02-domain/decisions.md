# Спорные решения доменной модели

### Р-1. TestResult - композиция в Run, а не агрегация

**Альтернатива:** агрегация - результат мог бы существовать сам по себе.

**Решение:** композиция Run "1" *-- "0..*" TestResult.

**Почему:** результат теста вне прогона бессмыслен: непонятно, когда и в каком окружении он получен и на какой коммит ссылается. Удаление прогона удаляет его результаты - иначе статистика считает фантомы. Кратность со стороны Run ровно 1: результат не может принадлежать двум прогонам (повтор создаёт свои результаты, а не переиспользует чужие). Со стороны результатов кратность 0..*, а не 1..*: по сценарию ВИ-06 прогон создаётся в статусе PENDING (шаг 3) раньше, чем появляется первый результат (шаг 6), а отменённый прогон может не иметь результатов вовсе.

**Что будет, если ошиблись:** «осиротевшие» результаты ломают расчёт флаки (И-3 сценария ВИ-04) и падают при построении отчёта; при кратности 1..* модель запрещала бы существование только что созданного прогона.

### Р-2. Кратность повтора - 0..1, а не 1

**Альтернатива:** Run --> "1" Run - каждый прогон обязан быть чьим-то повтором.

**Решение:** Run "0..*" --> "0..1" Run.

**Почему:** повтор - опциональное поведение (extend ВИ-07, условие «есть упавшие»). У исходного прогона повтора может не быть никогда, поэтому 0..1; повторов может быть сколько угодно, и все ссылаются на один исходный прогон.

**Что будет, если ошиблись:** объектная диаграмма не соберётся для первого же прогона без повтора - модель потребует несуществующий объект. В objects.puml это run-1189: на него ссылается повтор run-1201, а сам он ни на какой прогон не ссылается.

### Р-3. Привязка «набор - ветка» - отдельный класс BranchBinding

**Альтернатива:** атрибут ассоциации у связи «многие ко многим» CIIntegration -- TestSuite.

**Решение:** класс BranchBinding { +branch: String } с ассоциациями CIIntegration "1" -- "0..*" BranchBinding и BranchBinding "0..*" --> "1" TestSuite.

**Почему:** у связи «многие ко многим» атрибут «ветка» не имеет владельца: это не свойство интеграции (одна интеграция привязывает много веток) и не свойство набора (набор привязывается по-разному к разным CI). Это случай класса-ассоциации. Выбран обычный класс с двумя ассоциациями, а не UML-класс-ассоциация `(CIIntegration, TestSuite) .. BranchBinding`: класс-ассоциация допускает одну связь на пару, а одна интеграция может привязать один и тот же набор к нескольким веткам.

**Что будет, если ошиблись:** без класса поле пришлось бы дублировать в обеих таблицах связи (нарушение единственного источника истины) либо терять при миграциях.

### Р-4. Пакеты - по направлению изменчивости, ациклично

**Альтернатива:** разбиение по техническим слоям (репозитории/сервисы/контроллеры) либо плоская модель без пакетов.

**Решение:** три пакета по направлению изменчивости: management - стабильное ядро (что хранится: наборы, тесты), execution - изменчивая часть (что происходит: прогоны, результаты, отчёты, политика флаки), integration - внешний интерфейс (как мир попадает в систему). Зависимости: integration → management и execution → management; integration и execution друг от друга не зависят, из management нет ни одной исходящей ссылки. Ацикличность обеспечена направлением связей: ассоциации проведены от прогона и результата к набору и тесту (Run "0..*" --> "1" TestSuite, TestResult "0..*" --> "1" TestCase), а привязка ветки ссылается на набор (BranchBinding "0..*" --> "1" TestSuite).

**Почему:** ядро не должно дрожать от изменчивого: смена CI-провайдера или движка прогонов не трогает TestSuite/TestCase. Разбиение по слоям отражает реализацию, а не предметную область - модель должна пережить смену реализации.

**Что будет, если ошиблись:** при круговой зависимости (в первой версии TestSuite.launch(): Run и связь «набор - прогоны» вели из management в execution) любое изменение в execution вынуждало бы менять management, и «стабильный» пакет переставал быть стабильным.

### Р-5. «Флаки-тест» - атрибут, а не класс

**Альтернатива:** класс FlakyTest, отдельный от TestCase.

**Решение:** TestCase.isFlaky: Boolean (+ retryCount); правило выявления вынесено в FlakyPolicy.evaluate().

**Почему:** флаки - состояние теста, меняющееся по мере накопления истории, а не сущность. Отдельный класс породил бы дубль идентичности: тот же тест существовал бы дважды, и историю результатов пришлось бы разрывать между ними.

**Что будет, если ошиблись:** тест, ставший флаки, пришлось бы «переносить» между классами, теряя историю - именно её эвристика и анализирует (ВИ-04).

### Р-6. TestSuite - агрегация тестов; прогоны связаны обычной ассоциацией

**Альтернатива:** композиция - удаление набора удаляло бы его тесты и прогоны.

**Решение:** TestSuite "0..*" o-- "1..*" TestCase (агрегация); Run "0..*" --> "1" TestSuite (направленная ассоциация без ромба).

**Почему:** набор - лишь группировка для запуска (smoke, regress), один тест может входить в несколько наборов, поэтому часть разделяемая, а не принадлежащая: это агрегация, а не композиция. Композиция тестов оставила бы TestResult "0..*" --> "1" TestCase без тела: история результатов указывала бы на удалённые вместе с набором тесты. Прогоны не являются частью набора, это накопленная история, переживающая набор (README): для такой связи достаточно ассоциации, а её направление от Run к TestSuite исключает ссылки из management в execution (Р-4). Набор архивируется, а не удаляется физически, иначе обязательная ссылка Run → TestSuite повисла бы.

**Что будет, если ошиблись:** расформирование устаревшего набора стёрло бы тесты и всю историю: окно N для расчёта флаки обнулилось бы, статистика стабильности исчезла бы вместе с набором.
