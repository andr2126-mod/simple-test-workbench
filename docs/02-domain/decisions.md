# Спорные решения доменной модели

### Р-1. TestResult - композиция в Run, а не агрегация

**Альтернатива:** агрегация - результат мог бы существовать сам по себе.
**Решение:** композиция Run "1" *-- "1..*" TestResult.
**Почему:** результат теста вне прогона бессмыслен: непонятно, когда и в каком окружении он получен и на какой коммит ссылается. Удаление прогона удаляет его результаты - иначе статистика считает фантомы. Кратность со стороны Run ровно 1: результат не может принадлежать двум прогонам (повтор создаёт свои результаты, а не переиспользует чужие).
**Что будет, если ошиблись:** «осиротевшие» результаты ломают расчёт флаки (И-3 сценария ВИ-04) и падают при построении отчёта.

### Р-2. Кратность повтора - 0..1, а не 1

**Альтернатива:** Run --> "1" Run - каждый прогон обязан быть чьим-то повтором.
**Решение:** Run "0..*" --> "0..1" Run.
**Почему:** повтор - опциональное поведение (extend ВИ-07, условие «есть упавшие»). У исходного прогона повтора может не быть никогда, поэтому 0..1; повторов может быть сколько угодно, и все ссылаются на один исходный прогон.
**Что будет, если ошиблись:** объектная диаграмма не соберётся для первого же прогона без повтора - модель потребует несуществующий объект.

### Р-3. Привязка «набор - ветка» - класс-ассоциация Привязка

**Альтернатива:** атрибут ассоциации у связи «многие ко многим» CIIntegration -- TestSuite.
**Решение:** класс Привязка { +ветка: String } с ассоциациями CIIntegration "1" -- "0..*" Привязка и Привязка "0..*" --> "1" TestSuite.
**Почему:** у связи «многие ко многим» атрибут «ветка» не имеет владельца: это не свойство интеграции (одна интеграция привязывает много веток) и не свойство набора (набор привязывается по-разному к разным CI). Это случай класса-ассоциации. Прежнее решение «обойтись атрибутом» было непоследовательным: в модели поле нигде не появилось, а candidates.md и decisions расходились во владельце.
**Что будет, если ошиблись:** без класса поле пришлось бы дублировать в обеих таблицах связи (нарушение единственного источника истины) либо терять при миграциях.

### Р-4. Пакеты - по направлению изменчивости и зависимостей

### Р-4. Пакеты - по направлению изменчивости, ациклично

**Альтернатива:** разбиение по техническим слоям (репозитории/сервисы/контроллеры)
либо плоская модель без пакетов.

**Решение:** три пакета по направлению изменчивости: management - стабильное ядро
(что хранится: наборы, тесты), execution - изменчивая часть (что происходит: прогоны,
результаты, отчёты, политика флаки), integration - внешний интерфейс (как мир попадает
в систему). Зависимости строго ацикличные: integration → execution → management.
Ацикличность обеспечена конструктивно: операция launch() убрана из TestSuite, а связи
«набор - прогоны» и «тест - результаты» проведены от прогона и результата к набору
и тесту (Run "0..*" --o "1" TestSuite, TestResult "0..*" --o "1" TestCase) - из
management нет ни одной исходящей ссылки на execution.

**Почему:** ядро не должно дрожать от изменчивого: смена CI-провайдера или движка
прогонов не трогает TestSuite/TestCase. Разбиение по слоям отражает реализацию,
а не предметную область - модель должна пережить смену реализации.

**Что будет, если ошиблись:** при круговой зависимости (как было в первой версии:
TestSuite.launch(): Run и TestSuite o-- Run вели из management в execution) любое
изменение в execution вынудит менять management - стабильное ядро придётся
перекомпилировать из-за каждого нового интегрированного CI, и «стабильный» пакет
перестаёт быть стабильным.

### Р-5. «Флаки-тест» - атрибут, а не класс

**Альтернатива:** класс FlakyTest, отдельный от TestCase.
**Решение:** TestCase.isFlaky: Boolean (+ retryCount).
**Почему:** флаки - состояние теста, меняющееся по мере накопления истории, а не сущность. Отдельный класс породил бы дубль идентичности: тот же тест существовал бы дважды, и историю результатов пришлось бы разрывать между ними.
**Что будет, если ошиблись:** тест, ставший флаки, пришлось бы «переносить» между классами, теряя историю - именно её эвристика и анализирует (ВИ-04).

### Р-6. TestSuite - агрегация, а не композиция (тестов и прогонов)

**Альтернатива:** композиция - удаление набора удаляло бы его тесты и прогоны.

**Решение:** обе связи набора - агрегации: TestSuite "1" o-- "1..*" TestCase
(содержит тесты) и Run "0..*" --o "1" TestSuite (прогоны; линия проведена от прогона
к набору ради ацикличности пакетов - ромб остаётся у TestSuite).

**Почему:** набор - лишь группировка для запуска (smoke, regress), а ценность системы
- накопленная история. Композиция прогонов противоречила бы README (история
отслеживает динамику), а композиция тестов оставила бы TestResult "0..*" --> "1"
TestCase без тела: история результатов указывала бы на удалённые вместе с набором
тесты. Тесты, их результаты и прогоны переживают набор.

**Что будет, если ошиблись:** расформирование устаревшего набора стёрло бы тесты
и всю историю: окно N для расчёта флаки обнулилось бы, статистика стабильности
исчезла бы вместе с набором.
