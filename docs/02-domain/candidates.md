# Кандидаты в классы: существительные из scenarios.md

Приём: выписываем все существительные из сценариев и решаем для каждого - класс, атрибут, тип-перечисление или «не моделируем». Критерий: у класса есть идентичность (два объекта с одинаковыми полями - всё равно разные) и жизненный цикл; у атрибута - нет.

| Существительное из сценария | Решение | Почему |
| --- | --- | --- |
| набор тестов | класс TestSuite | ВИ-01, ВИ-06: набор запускают и привязывают к ветке; идентичность, жизненный цикл, теги |
| тест | класс TestCase | ВИ-04: у теста накапливается история результатов и есть версия; идентичность |
| прогон | класс Run | ВИ-01, ВИ-06: полный жизненный цикл PENDING → PASSED/FAILED/ERROR/CANCELLED; уникален даже при одинаковом наборе и коммите |
| результат теста | класс TestResult | ВИ-06 (шаг 6): создаётся при каждом прогоне; у одного прогона их много - «экземпляры» прогона |
| отчёт | класс Report | ВИ-06 (шаг 7): генерируется по завершённому прогону, своё время генерации и URL |
| история прогонов | не отдельный класс | коллекция Run/TestResult, а не сущность с собственным поведением; RunHistory - хранилище, компонент реализации |
| флаки-тест | не класс: TestCase с isFlaky = true | состояние теста, а не отдельная сущность; отдельный класс породил бы дубль идентичности (Р-5) |
| выявление и маркировка флаки (шаги ВИ-04) | операция FlakyPolicy.evaluate() | алгоритм без собственного состояния и идентичности; отдельный класс-сервис (FlakyDetector) исключён как компонент реализации, правило живёт в FlakyPolicy |
| commitSha | атрибут Run.commitSha | значение без идентичности и жизненного цикла |
| triggerSource | атрибут Run.triggerSource (тип TriggerSource) | характеристика прогона: кто/что его запустило |
| статус прогона (PENDING, PASSED, FAILED, ERROR, CANCELLED) | enum RunStatus (тип) | конечный набор значений без поведения; ERROR ≠ FAILED - принципиально для статистики |
| статус результата | enum ResultStatus (тип) | то же |
| summaryUrl | атрибут Report.summaryUrl | ссылка, не сущность |
| интеграция | абстрактный класс Integration | ВИ-05, И-1 ВИ-06: общая часть настроек внешней интеграции (идентификатор, токен, проверка токена); CIIntegration - её единственная конкретизация, другие источники событий добавляются как наследники |
| интеграция с CI (настройка) | класс CIIntegration - кандидат, новый | настройка живёт своим циклом (создать/изменить/отозвать); меняется независимо от прогонов (ВИ-05) |
| токен CI | атрибут Integration.encryptedToken | секрет, а не объект с жизненным циклом; хранится в зашифрованном виде (traceability, ВИ-05) |
| проверка токена | операция Integration.authenticate() | шаг 2 и И-1 сценария ВИ-06; поведение, общее для всех интеграций |
| привязка набора к ветке | класс BranchBinding - кандидат, новый | ветка - свойство пары «интеграция - набор», а не самих классов; у связи «многие ко многим» атрибут требует собственного класса (Р-3) |
| ветка | атрибут BranchBinding.branch | значение без идентичности; владелец - привязка |
| окно истории N, пороги эвристики | класс FlakyPolicy - кандидат, новый | правило меняется конфигурацией без релиза (примечание к ВИ-04) - аналог «лимита книг» из примера |
| isFlaky, retryCount | атрибуты TestCase | нет собственной идентичности |
| версия теста | атрибут TestCase.version - кандидат, новый | при правке теста окно истории сбрасывается (И-4 сценария ВИ-04): старые результаты не характеризуют новую версию |
| окружение | атрибут TestResult.environment - кандидат, новый | эвристика сравнивает PASSED и FAILED на одинаковом коммите И окружении; без атрибута сравнение не формализовать |
| причина сбоя | атрибут Run.errorReason | диагностика ERROR-прогонов, значение без жизненного цикла |
| идемпотентный ключ | атрибут Run.idempotencyKey | технический атрибут, защита от дубликатов прогона (И-4 сценария ВИ-06) |
| идентификатор Run | атрибут Run.id | возвращается CI-серверу при приёме запроса и используется для опроса статуса (ВИ-06, шаги 4 и 8) |
| лог | не моделируем | внешний артефакт; в модели только ссылка logsUrl |
| CI-сервер | не моделируем | внешняя система, актёр вне границы |
| репозиторий, событие в репозитории | не моделируем | внешнее окружение; событие попадает в систему как запрос CI-сервера |
| среда исполнения тестов | не моделируем | внешнее окружение; её сбой отражается как TestResult.status = ERROR и причина сбоя |
| gate сборки | не моделируем | понятие CI, живёт за границей системы |
| тестировщик, разработчик | не моделируем | актёры - люди, вне предметной области |
| TestAPI, TestRunner, ReportService | компоненты реализации, не доменные классы | их взаимодействие описывает sequence-диаграмма; в доменной модели - сущности и правила |
| сводка, список флаки-тестов, динамика падений | не моделируем | представления (артефакты отображения), а не сущности |
